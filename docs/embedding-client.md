# Embedding and extending the admin client

This guide is the host contract for serving the GoAdmin UI and adding or removing
pages. It applies to the version of `goadmin` pinned by the host's `go.mod`;
rebuild the client from that same version whenever its Vue source or an extension
changes. `goadmin` publishes source and embedded templates, but its Go module
does not contain a ready-to-serve `public/dist` bundle for a host extension.

## One page crosses four boundaries

A navigation item is only a link. A working page requires all of these:

1. A `host.Feature` descriptor contributes a menu `Href` and, when the feature
   owns client code, a `ClientExtensionRequirement` with the extension key and
   source fingerprint.
2. The feature registers an authorized GET route at that exact `Href`. Render
   the page with `host.App.Render(c, "section/PageName", props)`; do not return a
   separate HTML document for an internal admin menu route. Protect mutation
   routes separately with the same permission policy.
3. The client extension contains `Pages/section/PageName.vue`. The path after
   `Pages/`, without `.vue`, is the case-sensitive Inertia page name. Keep shared
   components outside `Pages/`, since every `.vue` there is registered as a page.
4. The host builds that extension together with the pinned GoAdmin client,
   embeds the resulting `dist`, serves it through `PublicFS`, and supplies the
   compatible templates through `TemplateFS`.

For example, a menu `Href` of `/reports` can render `reports/Index` from
`Pages/reports/Index.vue`. The route handler must call `app.Render(c,
"reports/Index", props)` after its authorization check. A regular HTML response
at `/reports` breaks Inertia navigation even when the URL and menu are correct.

## Build and embed

Create an extension source directory and a version-1 JSON manifest beside it.
The manifest's `sourceRoot` is relative to the manifest file. Its `fingerprint`
is generated by `fingerprintSource` from
`resources/scripts/materialize-admin-extensions.cjs`; do not hand-edit the
fingerprint or reuse it after changing source files. The `key` must be unique
across all manifests. The server's `ClientExtensionRequirement` must use the
same key, API version, and fingerprint. See the manifest materializer tests for
accepted shapes and dependency rules.

Build from a writable copy of the **pinned module's** `resources/` source. Point
`VITE_ADMIN_EXTENSION_MANIFESTS` at the extension manifest and
`VITE_ADMIN_PUBLIC_ROOT` at the directory that the host will embed. The builder
resolves dependencies, imports extension pages, and writes `dist` plus
`dist/admin-extensions.manifest.json`. `npm ci` and `npm run build-only` are the
reproducible commands in that copied `resources/` directory. The build checks
the core assets; when the `views/` source is present, it also checks every asset
referenced by its embedded templates. A host may provide its own template, but
its referenced asset names must match the files it embeds. The default template uses `js/app.js`, `css/app.css`, and `favicon.ico`.
The older `css/vendor.css` reference was stale and is no longer needed.

The built-in client reads `VITE_ADMIN_CSRF_COOKIE_NAME` at build time and falls
back to `csrf_token`, matching the default of `host.NewCSRFService`. If the host
configures a different
`APP_ADMIN_CSRF_TOKEN_NAME` / `host.AdminConfigInput.CSRFTokenName`, set the build
variable to the **same** cookie name before `npm run build-only`. The header
remains `X-CSRF-Token`. A cookie-name mismatch can make the login page render
while authenticated writes fail. Never put a CSRF secret in the build variable;
it is a public cookie name.

At host startup, construct a registry from the server features, then call
`host.BuildClientBundleValidation(registry, publicFS)` against the exact
`fs.ReadFileFS` being served. `host.New` performs the same validation against `host.Config.Public`
and supply that same `publicFS` and the matching `templateFS` to
`host.BuildBootstrapOptions`. The validator fails before boot for a missing or
empty entry JavaScript, stylesheet, favicon, missing manifest, or a drifted
extension. `host.CoreTemplateFS()` provides the default templates; hosts that
build their own bundle must provide their built public FS rather than assume
`host.CorePublicFS()` contains that bundle. In local Vite mode, the development
proxy must route `/.admin-extensions/` to Vite.

GoAdmin's entry filenames are stable. When deploying a new bundle, version the
asset URLs in the host's served template or use a cache policy that makes the
entry JS/CSS revalidate. This prevents an already-open tab from continuing to
load a cached client that does not know a newly added page. The host must
publish matching server code, `dist`, manifest, and templates as one release.
The built-in static handler always sends the current fixed-name entry JS/CSS:
it ignores date revalidation and omits `Last-Modified`, because embedded files
have a zero modification time even after their contents change. Hashed chunks
keep the normal static-file policy. Hosts serving their own embedded FS must
use the same policy or version the entry URLs.

## Add, change, or remove a page

To add a page, create its Vue file, register the authorized GET route using
`app.Render`, and optionally add a menu item pointing to that route. Rebuild and
embed the client; update the server requirement fingerprint. A page can exist
without a menu item if it is reached by another authorized flow. To change a
page, rebuild the client and its fingerprint even when the server route stays
the same. To remove a page, remove the menu entry and route, remove unused
mutation routes, delete its Vue file, and rebuild. If the whole extension is
removed, remove its manifest and server requirement together.

`ClientBundleValidation` checks extension identity and the core files, but it
does not prove that every `app.Render` page name exists or every menu URL has a
route. Hosts should test that contract at their feature boundary and run a
browser smoke test for at least one navigation and one authenticated mutation.
A useful failure matrix is:

- Blank login: check `/public/dist/js/app.js` and `/public/dist/css/app.css`,
  `PublicFS`, and the browser console.
- Fallback page: compare `app.Render` name with the Vue path, then rebuild and
  reload the tab.
- Standalone document in an internal dialog: use an Inertia response from the
  menu route instead of a separate HTML page.
- Failed write after login: check the cookie name, `X-CSRF-Token`, session, and
  permission gate in the browser network trace.

The shared Vite build uses `base: './'`. Lazy page chunks and their CSS resolve
relative to the emitted JavaScript URL, so embedded bundles continue to load
under `/public/dist` or a host asset prefix. Keep this setting when adapting the
build; an absolute root base sends lazy CSS requests to the host's `/css` route.
